# `extern c`: Real FFI, and the First Real Interpreter/Backend Asymmetry

**Status:** Implemented
**Document:** `0048-ffi.md`

---

# Motivation

`docs/std/strings/0007-ffi.md`, in full:

```ax
extern c puts(text: cstr)
```
"Use `to_cstr()` for C interop." This phase implements exactly that:
top-level `extern c name(params) [-> returnType]` declarations, callable
with the exact same `name(args)` syntax as any real Axea function, a new
`cstr` type (representationally identical to `str`, but a genuinely
distinct Axea type reachable only via a new `.to_cstr()` method), and a
narrow, explicit allowlist of FFI-safe parameter/return types
(`i32`/`bool`/`str`/`cstr`, plus `unit`/omitted for a return type).

```ax
extern c puts(text: cstr)
extern c abs(x: i32) -> i32

greet(name: str) -> i32
{
    puts(name.to_cstr())
    return 1
}
```

**The first feature this session where the interpreter and the compiled
backend are not equally capable, by necessity, not by oversight.** Every
prior feature was verified identical across both backends via diffing
real output. `extern` breaks that symmetry for real: the compiled
backend genuinely links against the real libc `puts`/`abs`/whatever else
a user declares (`clang -x ir` resolves the symbol at compile time,
verified directly by calling `abs`, a function this implementation never
hand-wrote anywhere); the interpreter is a C++ program with no dynamic
linker of its own, so it can only ever call functions someone
hand-implemented in C++ ahead of time. This phase hand-implements exactly
two (`puts`, `abs`) - enough to prove the mechanism and to keep
`examples/ffi.ax` diffable end to end - and documents the gap honestly
rather than either faking a general FFI bridge or silently leaving the
interpreter unable to run any extern-using program at all.

# Design: `cstr` Is `str`, Reached Through One Deliberate Door

**Representationally, `cstr` and `str` are the same thing** - both a
bare, null-terminated `i8*` (`docs/language/0042-string.md`'s own Design
section already established `str` is always null-terminated, so it was
already a valid C string with zero new work). Given that, `llvmType("cstr")`
returns the identical `"i8*"` `llvmType("str")` does - no new
representation, no new runtime cost.

**But `str` does not implicitly convert to `cstr`.** The design doc's own
"Use `to_cstr()` for C interop" phrasing reads as a deliberate step, not
a formality, mirroring "String lends a str"'s own one-way (never
implicit-both-ways) coercion rule. `TypeKind::CStr` is a genuinely
distinct `TypeKind` from `TypeKind::String` (`str`'s own kind); the sole
legal way to produce a `cstr` value is `.to_cstr()`, callable on anything
str-coercible (`str` or `String`, reusing `isStrCoercible` a fourth way).
At the LLVM layer, `.to_cstr()` (`IrToCstr`) is consequently a real
instruction that does *nothing representationally* - `resolveStrPtr` the
object to a bare `i8*`, then a self-bitcast (`i8*` to `i8*`) purely so
the destination register is independently defined like every other
instruction's dest here, rather than aliasing the source register
directly. `-O1` folds it away entirely; it exists at `-O0` only to keep
the type distinction real without inventing a genuinely new
representation to enforce it.

**FFI-safe types are a real, narrow allowlist - not "anything goes."**
`isFfiSafeType` accepts exactly `i32`, `bool`, `str`, `cstr` (plus
`unit`/omitted for a return type). `char` is explicitly excluded - its
`i24` width (`docs/language/0044-char.md`) has no C equivalent, and
declaring an extern parameter as `i24` when the real C signature expects
`char` (`i8`) or `int` (`i32`) would silently corrupt every argument
after it in the real C calling convention. Every collection/`String`/
`Buffer` is excluded too - each is a heap object with an Axea-specific
memory layout no C caller could correctly interpret. Validated once, at
registration time (`TypeChecker::registerSignatures`), for every extern's
own param and return types - not deferred to each individual call site.

**A real ABI question, verified empirically before committing to it, not
assumed.** The design doc's own `extern c puts(text: cstr)` has *no*
declared return type - but real libc `puts` returns `int`, not `void`.
Does declaring the LLVM-level signature as `void` and calling the
genuine `int`-returning symbol actually work? Verified directly with a
standalone `.ll` file before writing any interpreter/backend code around
it: yes - the caller's own choice not to generate code reading a return
register is always safe on the calling conventions this backend targets;
the callee still executes correctly and its own return value is simply
never touched. This is the same reasoning `emitStructPrintHelpers`
already relies on for a discarded `printf` result, just applied to a
whole-function return instead of one already-known-discarded call.

**A real, deliberate name-collision guard.** A real Axea function and an
`extern c` declaration sharing one name would otherwise let
`CallExpr`'s own functions-before-externs lookup order silently pick one
over the other with no warning - rejected explicitly at registration
time, in both declaration orders, rather than left as a silent shadowing
footgun.

# Parsing: A New Keyword, and a Deliberately Simpler Param Grammar

`extern` joins the keyword table for the first time since `for`/`in`.
`c` (the calling convention) is a bare identifier check at parse time,
not its own keyword - the same "recognized by literal text, not a
reserved word" trick `String`/`Buffer`'s own constructors already use -
so `extern rust foo(...)` parses fine syntactically and is rejected with
a clear message, rather than being a lexer-level dead end.
`parseExternParam` is a deliberately *simpler*, dedicated parse than the
existing `parseParam` (no `read`/`write`/`take` capability-prefix
support) - a plain C function signature has no such concept, and
allowing one to parse (even if later rejected) would be a confusing,
pointless grammar extension.

```text
$ ax ast examples/ffi.ax
Extern(puts)
  Param(text: cstr)
Extern(abs)
  Param(x: i32)
  Returns(i32)
```

# Type Checking: A Second Signature Table, Consulted Alongside the First

`registerSignatures` gained a parallel `externs_` map (keyed the same way
`functions_` already is) rather than folding `ExternDecl` into
`functions_` itself - a real, different AST node (no body), even though
its own `(params, returnType)` shape happens to coincide with
`FunctionDecl`'s. `CallExpr`'s own type-checking was restructured to
extract `(params, returnType)` from whichever table actually has the
callee, then proceed completely generically from there - the existing
array-to-slice and String-to-str call-boundary coercions apply to extern
calls exactly as they already do to ordinary ones, with zero duplicated
logic.

```text
$ ax capabilities bad.ax   # extern c foo(x: char)
error: extern function 'foo' has an unsupported parameter type: char
(only i32, bool, str, and cstr are FFI-safe)
```

---

# Capability Checking / Region Checking: Zero New Code, Confirmed Not Assumed

Both passes already degrade gracefully for an unrecognized callee name
(`functions_.find(...)` failing silently returns/skips rather than
crashing) - exactly the behavior an extern call needs, since none of its
own possible argument types (`i32`/`bool`/`str`/`cstr`) ever need
capability inference or region tracking in the first place. Confirmed by
tracing both call sites directly, not assumed by analogy: an extern call
through a borrowed `str` parameter (`greet(name: str) { puts(name.to_cstr()) }`)
correctly infers `Read`, and the call itself passes `RegionChecker`
without any new code.

# `IrGenerator` / `LlvmIrEmitter`: Registration, Not Lowering

An `ExternDecl` has no body, so there is nothing to *lower* - only to
*register*, into a new `IrProgram.externs` list (parallel to `.functions`,
carrying just `(name, paramTypes, returnType)` - no param names needed,
since extern parameters are never referenced by name anywhere). `IrCall`
itself needed **zero** changes: it already lowers a call purely by
callee name and argument registers, with no awareness of whether that
name resolves to a `define`d or `declare`d symbol - that distinction only
matters once `LlvmIrEmitter` decides what text to emit for the callee
itself. `LlvmIrEmitter` emits one real LLVM `declare` per extern
(alongside the existing fixed `malloc`/`printf`/`strlen` externs, now
joined by user-specified ones) and registers each into the exact same
`functionParamTypes_`/`functionReturnTypes_` maps ordinary functions use
- so the existing String-lends-a-str call-boundary resolution applies to
an extern call automatically, with no special-casing.

```text
$ ax llvm-ir examples/ffi.ax
declare void @puts(i8*)
declare i32 @abs(i32)
```

# Interpreter: An Honest, Explicit Allowlist

`callExtern` is consulted only when `call->callee` isn't a real,
lowered-and-registered Axea function - a small `if (name == "puts") ...`/
`if (name == "abs") ...` chain, each hand-implemented to match its real
libc counterpart's *observable* behavior exactly (verified via the usual
diff-against-compiled-output discipline: `examples/ffi.ax` produces
byte-identical output on both backends, including the `abs` call this
implementation never wrote a general bridge for). Any other extern name
throws a clear, specific error - `"extern function 'X' has no
interpreter implementation"` - rather than silently doing nothing or
crashing on an unrelated error. `.to_cstr()` is a pure identity in the
interpreter (both `str` and `cstr` are the same bare `std::string`), the
same "representational no-op, real type-level step" story the LLVM
backend's own bitcast has.

```text
$ ax run bad.ax   # extern c getpid() -> i32  x = getpid()
error: extern function 'getpid' has no interpreter implementation -
only a small allowlist of well-known libc functions is hand-implemented
this phase
$ ax llvm-ir bad.ax | clang -x ir - -o out && ./out   # this, meanwhile, just works
```

# Worked Example

`examples/ffi.ax`:

```ax
extern c puts(text: cstr)
extern c abs(x: i32) -> i32

greet(name: str) -> i32
{
    puts(name.to_cstr())
    return 1
}

called = greet("hello from axea")

message = String("owned strings work too")
called2 = puts(message.to_cstr())

magnitude = abs(0 - 42)
```

```text
$ ax run examples/ffi.ax
hello from axea
owned strings work too
called = 1
message = owned strings work too
called2 = ()
magnitude = 42
$ ax llvm-ir examples/ffi.ax | clang -x ir -O1 - -o out && ./out
# byte-for-byte identical (also re-verified at -O0)
```

`magnitude = 42` confirms `abs(0 - 42)` really calls the genuine libc
`abs` when compiled and the hand-implemented interpreter allowlist entry
when interpreted, and that the two agree - the one call in this example
this implementation could have gotten subtly wrong (an off-by-one in the
hand-written `abs`, or a real ABI mismatch) but didn't, because both
paths were actually run and diffed rather than reasoned about in the
abstract.

# Known Imprecision / Out of Scope (By Design, Not Oversight)

- **The interpreter can only call a small, hand-implemented allowlist**
  (`puts`, `abs`) - any other extern name is a clear runtime error when
  interpreted, even though the exact same program compiles and runs
  correctly. A real, load-bearing asymmetry, not a bug - see Motivation
  above.
- **Only the `c` calling convention.** No other convention exists to
  need supporting yet.
- **No variadic externs** (`printf`-style `...`) - every extern's own
  parameter list is fixed-arity, matching every ordinary Axea function.
- **No struct-by-value FFI.** Only the four FFI-safe scalar/pointer types
  may cross the boundary; passing a struct to/from C would need a real
  ABI layout decision this phase doesn't make.
- **No `extern` blocks** (grouping several declarations under one
  `extern c { ... }`) - each declaration repeats `extern c` individually,
  matching the design doc's own single-declaration-at-a-time examples.

# Guiding Rule

> Every backend-parity claim earlier in this session ("the interpreter
> and the compiled backend agree, verified by diffing") was true because
> both backends were equally capable of expressing the same idea - a
> loop, a heap allocation, a runtime scan. `extern` is the first feature
> where that equal capability is actually impossible without a much
> larger dependency (a real dynamic linker inside the interpreter itself)
> that this project has no reason to take on. The discipline that stays
> constant even when the capability doesn't: verify the ABI question
> that actually matters (does a void-declared wrapper around a real
> int-returning symbol work?) empirically before writing code around the
> answer, hand-implement enough of the gap to keep the one example that
> matters (`examples/ffi.ax`) genuinely diffable, and write down exactly
> where the two backends now diverge rather than letting a future reader
> discover it by surprise.
