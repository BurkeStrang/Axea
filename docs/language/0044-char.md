# `char`: A Single Unicode Scalar Value, and the First Type That Needs Its Own LLVM Width

**Status:** Implemented
**Document:** `0044-char.md`

---

# Motivation

`docs/std/strings/0003-char.md` specs `char` as a Unicode scalar value,
shown with three literals: `'A'`, `'é'`, `'🚀'` - one ASCII byte, one
2-byte UTF-8 sequence, one 4-byte UTF-8 sequence. This phase implements
exactly that: the literal syntax, equality (`==`/`!=`), ordering
(`<`/`<=`/`>`/`>=` by codepoint), and use as a parameter/return/local/
struct-field type - deliberately excluding arithmetic (`char + char` is
rejected, mirroring Rust), any `i32 <-> char` conversion, and use as a
`Map`/`Set` key.

```ax
a = 'A'
accented = 'é'
rocket = '🚀'

isEqual = a == 'A'
isLess = a < accented
```

**The real discovery this phase**: char is the first type whose *runtime
representation* would collide with an existing one if given the obvious
choice. Every Unicode codepoint fits in 21 bits (max `0x10FFFF`), which
makes `i32` the natural LLVM width - but `i32` is already `i32`'s own
width. Two Axea types sharing one LLVM type has never happened before
(every collection's own header shape has been deliberately unique, or -
for `String`/`List<i8>` - deliberately, harmlessly identical since `i8`
isn't nameable in source). A `char` register that's *textually*
indistinguishable from an `i32` one would break the one thing every prior
`isXType` predicate in this codebase has relied on: that a register's own
LLVM type string is enough, by itself, to know what to do with it - most
concretely, the top-level print dispatch would have no way to choose
between printing a decimal number and printing a Unicode character. The
fix: give `char` a genuinely different integer width, `i24` - plenty for
the full Unicode range, and never confusable with `i32` again.

# Design: `i24`, and a Real UTF-8 Encoder

A `char` value is a plain `i24` SSA register holding its own codepoint
directly - no heap allocation, no pointer, the same "just a scalar" shape
`i32`/`bool` already have. `llvmType("char")` returns `"i24"`;
`isCharType` is an exact match on that string, mirroring
`isStringType`/`isBufferType`'s own exact-match style. Every arithmetic/
comparison LLVM opcode is width-agnostic text (`icmp eq i24 %x, %y` is as
valid as `icmp eq i32 %x, %y`), so equality and ordering both work with
**zero** new opcode-selection code once a `char` register is typed `i24` -
the existing `binOpMnemonic` dispatch and `emitBinOp`'s own
`<< lhsType <<` splicing already generalize for free.

**Printing needs real work, because a codepoint isn't its own display
form.** Unlike every prior scalar (`i32` prints as decimal, `bool` as
`true`/`false`), a `char`'s printed form is a *variable-length byte
sequence* - `'🚀'` (codepoint `0x1F680`) must print as its own 4-byte UTF-8
encoding, not as the number `128640`. `encodeCharUtf8` is a new shared
helper (mirroring `resolveStrPtr`/`ensureBufferCapacity`'s own "small
reusable sub-computation" precedent): given a runtime `i24` codepoint
register, it mallocs a fixed 5-byte buffer (max 4 UTF-8 bytes + a null
terminator) and branches on the codepoint's own range (`<= 0x7F`,
`<= 0x7FF`, `<= 0xFFFF`, else) to decide how many bytes to emit and what
bit pattern each one gets - `lshr`/`and`/`or`/`trunc` compute each byte's
value, matching the standard UTF-8 encoding table exactly. This is the
first genuinely *value-range-branching* runtime routine in this codebase
(every prior conditional - `Buffer`'s own grow-or-not branch included -
branches on a single yes/no test; this branches four ways on where a
value falls in a range), but it's still a bounded, straight-line decision
tree, not a loop - no `phi` needed, same as everywhere else in this
backend.

**No validation needed at the encoding step.** `Parser::decodeCharLiteral`
is the *only* place a `char` value is ever produced from scratch (no
`i32 -> char` cast exists), and it already rejects anything that isn't a
single well-formed, non-overlong, non-surrogate Unicode scalar value at
parse time - so by the time a codepoint reaches `encodeCharUtf8` at
runtime, whether it arrived via a literal, a parameter, a struct field, or
a `List<char>` element, it is *always* already valid. This is the same
"trust internal invariants, validate only at the boundary" principle this
whole codebase already follows, applied to a brand-new boundary (parsing)
rather than a function-call one.

**Three separate print call sites needed the exact same fix, not one.**
Unlike `String`/`Buffer` (each with exactly one collision to guard
against), `char` can appear as a struct field *and* as an array/List/
Deque element, and each of those has its own, independently-hand-written
print dispatch (`emitStructPrintHelpers`, the fixed-array branch, and the
List/Deque "first element + loop body" branches - five call sites in
total, since List and Deque each print their first element and their
loop-body element separately). Every one of them already had a 3-way
`i32`/`i1`/`i8*` dispatch falling through to "must be a nested struct
pointer" for anything else - exactly the shape that would misinterpret an
unhandled `i24` register as a garbled struct pointer type and try to call
a print helper for a struct that doesn't exist. This was caught by
actually running the diff-against-compiled-output discipline on a struct
field and a `List<char>`/`Deque<char>`, not by inspection - see Interpreter
below.

**One subtlety inside `emitStructPrintHelpers`.** Unlike every other emit
function in this backend, struct-print helpers hand-track their own
register counter (a bare `int nextReg`) rather than going through a real
`FunctionContext`. `encodeCharUtf8` needs a real `FunctionContext` (it
calls `allocateRegister`/uses `fctx.nextLabel` internally), so fixing this
call site needed a small bridging `FunctionContext` declared *once*,
outside the per-struct loop - not per-field - specifically so its own
`nextLabel` counter keeps incrementing uniquely across every `char` field
in every struct. Declaring it per-field instead (the first version
written) was a real, caught bug: two `char` fields in the *same* struct
would each start their own label numbering from `0`, producing two
identically-named basic blocks (`char.utf8.len1.0`, etc.) inside the one
shared `@axea.print.<Name>` function - invalid LLVM IR. Caught directly by
testing a two-`char`-field struct before writing this up.

# Parsing: Raw Bytes at the Lexer, a Real Decoder in the Parser

`Lexer::lexChar` mirrors `lexString` exactly - scan raw bytes until the
closing `'`, no escape sequences (matching `lexString`'s own "no escapes
at all" simplification). This is safe for multi-byte UTF-8 content
(`'é'`, `'🚀'`) even though the scan only ever compares against the ASCII
byte `'` (`0x27`): a UTF-8 continuation byte (`0x80`-`0xBF`) can never
equal it.

`Parser::decodeCharLiteral` does the real work: reads the leading byte to
determine the sequence length (1-4 bytes, by its own high-bit pattern),
decodes the codepoint from the leading byte's low bits plus each
continuation byte's own 6 bits, and validates three things a lexer-only
approach couldn't: the byte count matches the length the leading byte
promised (rejects `''`/`'ab'`), the codepoint isn't below that length's
own minimum value (rejects overlong encodings), and the codepoint is
neither above `0x10FFFF` nor in the surrogate range `0xD800..0xDFFF`
(rejects invalid Unicode scalar values). `parseTypeName()` needs no
changes at all - `char` in type position is a bare identifier, same as
`i32`/`bool`, falling through the existing final `return name.text;`.

```text
$ ax ast examples/char.ax
Assignment(a)
  Char(65)
$ ax capabilities bad.ax   # x = ''
error: empty char literal
$ ax capabilities bad.ax   # x = 'ab'
error: char literal must contain exactly one character, found 2 byte(s)
```

# Type Checking: Ordering Needed a New Rule, Arithmetic Didn't

`TypeKind::Char` already existed as an unused enum value (left over from
`docs/language/0005-type-system.md`'s original broader sketch) - this
phase is the first to actually wire it up: `resolveType`'s primitive map
gains `"char" -> TypeKind::Char`, `typeName` gains the reverse case, and
`CharExpr`'s own `checkExpr` case returns it directly.

Equality needed **zero** new code: `EqualEqual`/`BangEqual` already just
check `leftType == rightType` with no per-type special-casing, so
`char == char` type-checked correctly the moment `TypeKind::Char` existed.
Arithmetic also needed zero new code: `requireInt` already only accepts
`i32`, so `char + char` was rejected automatically, for free, the instant
`char` became a real type - no denylist entry needed, since `requireInt`
was already an allowlist of exactly one type. Ordering is the one
genuinely new rule: `requireInt` is shared by arithmetic *and* ordering
today, and loosening it to accept `char` would have also loosened
arithmetic (not wanted - `char - char` shouldn't type-check, mirroring
Rust's own choice). A new `requireOrdered` helper accepts `(i32, i32)` or
`(char, char)`, but not a mix - `<`/`<=`/`>`/`>=` now call that instead,
while `+`/`-`/`*`/`/` keep calling the original, still-`i32`-only
`requireInt`.

`char` needed **no** struct-field/parameter/return-type rejection helper
either - unlike every collection (`rejectListAsFieldType` and friends),
which are all denylisted from struct fields, a plain value type like
`char` is *allowed* everywhere by default, the same "no restriction needed"
story `i32`/`bool` already have.

```text
$ ax capabilities bad.ax   # x = 'a' + 'b'
error: arithmetic/comparison requires i32 operands, found char and char
$ ax capabilities bad.ax   # x = 'a' < 5
error: comparison requires two i32 or two char operands, found char and i32
```

# Capability Checking / Region Checking: Zero and One Line

`CapabilityChecker` needed literally no changes - `CharExpr` has no
sub-expressions and no mutating methods, so it already falls through
`inferExpr`'s existing "no sub-expressions" comment-only case, the same
way `IntegerExpr`/`BoolExpr`/`StringExpr` already do.

`RegionChecker::regionOfExpr` needed exactly one line: `CharExpr` joins
`IntegerExpr`/`BoolExpr`/`StringExpr` in the literal group that returns
`Region::Owned` unconditionally - a `char` is a plain, freely-copyable
value with nothing to borrow or alias, the same story every other
primitive literal already has.

# `IrGenerator`: A New Constant Kind, Not a Reused One

`IrConstChar{codepoint}` is a genuinely new instruction, not
`IrConstInt` reused with a marker - even though both just carry a 32-bit
constant, `IrConstInt`'s own `inferTypesInList` entry always resolves to
`"i32"`; a shared instruction type would have made it impossible for the
LLVM backend to tell an `i32` constant from a `char` one apart *before*
even reaching the `i24`-vs-`i32` distinction. `CharExpr`'s own lowering is
a one-line `emit(ctx, IrConstChar{codepoint})`, mirroring `IntegerExpr`'s
own `IrConstInt` lowering exactly.

```text
$ ax ir examples/char.ax
  %3 = const.char 65
  %4 = const.char 233
  %5 = const.char 128640
  %7 = binop EqualEqual %3, %6
```

# Interpreter: `char32_t`, and the Same Encoder Written Twice on Purpose

```cpp
char32_t // added directly to the Value variant
```

Unlike `String`/`Buffer` (reference-semantics, `shared_ptr`-wrapped),
`char` is a plain value exactly like `i32`/`bool` - `char32_t` (a real,
distinct C++ type, not an alias for `std::int64_t`) is added directly to
the `Value` variant with no wrapper struct needed. `CharExpr` evaluation
is a one-line `static_cast<char32_t>(codepoint)`; `asInt` (shared by
arithmetic *and* ordering, mirroring `requireInt`/`requireOrdered`'s own
split at the type-checking layer) gained a `char32_t` branch, safe because
`TypeChecker` already guarantees a `char` value only ever reaches it via
the ordering path.

`toString` gained a small `encodeUtf8` helper - deliberately a **second,
independent implementation** of the exact same encoding rules
`LlvmIrEmitter::encodeCharUtf8` hand-emits as LLVM IR, written in plain
C++ instead. Not shared, per this codebase's "separate over shared"
convention for interpreter-vs-backend logic (they're different
*operations* - one runs at compile time producing IR text, the other runs
directly), but verified to agree byte-for-byte via the same
diff-against-compiled-output discipline every prior collection has used.

**The struct/array/List/Deque print-dispatch bug** (see Design above) was
caught exactly this way: `'🚀'` as a bare top-level binding printed
correctly on the very first try (the top-level dispatch was written and
tested first), but a `struct { c: char }` and a `List<char>` both failed
to even *compile* at the LLVM layer (`use of undefined value
'@axea.print.2'`) until their own dedicated `isCharType` branches were
added - three more genuinely separate call sites than `String`/`Buffer`
ever needed, each found by actually running the diff, not by reading the
code.

# Worked Example

`examples/char.ax`:

```ax
struct Letter
{
    value: char
    ordinal: i32
}

first = Letter { value: 'A'  ordinal: 1 }

a = 'A'
accented = 'é'
rocket = '🚀'

isEqual = a == 'A'
isNotEqual = a != accented
isLess = a < accented
isGreaterOrEqual = accented >= a

letters = List<char>()
appended1 = letters.push('a')
appended2 = letters.push('é')
appended3 = letters.push('🚀')
letterCount = letters.length
```

```text
$ ax run examples/char.ax
first = Letter { value: A, ordinal: 1 }
a = A
accented = é
rocket = 🚀
isEqual = true
isNotEqual = true
isLess = true
isGreaterOrEqual = true
letters = [a, é, 🚀]
appended1 = ()
appended2 = ()
appended3 = ()
letterCount = 3
$ ax llvm-ir examples/char.ax | clang -x ir -O1 - -o out && ./out
# byte-for-byte identical (also re-verified at -O0)
```

`isLess = true` confirms codepoint ordering (`'A'` is `65`, `'é'` is
`233`); `letters = [a, é, 🚀]` confirms a `List<char>` correctly
round-trips a 1-byte, a 2-byte, and a 4-byte UTF-8 character through
construction, `.push`, and printing, both interpreted and compiled.

# Known Imprecision / Out of Scope (By Design, Not Oversight)

- **No `i32 <-> char` conversion.** No cast syntax exists in this
  language yet; a future `as`-style conversion (or a `char::from_u32`-
  style constructor) would need explicit validation against the surrogate
  range, mirroring `decodeCharLiteral`'s own checks.
- **Not a valid `Map`/`Set` key type.** `registerKeyRuntime` has no `char`
  case - mirrors `String`'s own identical first-phase restriction.
- **No `.to_uppercase()`/`.is_alphabetic()`/etc.** No Unicode
  property tables exist in this compiler at all; `char` is purely a
  scalar-value carrier this phase.
- **No escape sequences in literals** (`'\n'`, `'\''`, `'\u{1F680}'`).
  Mirrors `lexString`'s own identical "no escapes at all" simplification -
  a literal's bytes are taken completely literally.
- **`char` is not hashable, not orderable against anything but another
  char** (no `char < i32`, even though both are ultimately integers) -
  a deliberate type-safety choice, not a missing feature.

# Guiding Rule

> Every type built so far in this codebase got its own LLVM
> representation for free, simply by being a new *shape* - a new struct
> layout, a new field count, a new pointer type. `char` is the first type
> whose natural representation would have been *structurally identical*
> to an existing one (`i32`) while meaning something completely
> different - the exact same problem `Buffer`'s header collision with
> `Deque<T>` was, except that collision was avoidable by adding an
> earlier-checked predicate, while this one had no such escape: two
> genuinely different 32-bit integer meanings cannot share one LLVM `i32`
> type and still be told apart downstream. Picking a different *width*
> (`i24`) rather than inventing a side-channel is the same "diverge only
> where the representation genuinely does" principle `docs/language/0032-slices.md`
> first named, applied to the one axis (bit width) this codebase hadn't
> needed to vary before.
